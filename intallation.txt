Part 12: Refresh Session Model:
A JWT refresh token should not remain valid only because its signature is valid. We also need a database record so the token can be:

Revoked during logout
Rotated during token refresh
Invalidated after password changes
Invalidated when an account is blocked
Tracked across multiple devices

We will store only a SHA-256 hash of the refresh token—not the raw token.
Complete security flow:
User logs in
Refresh JWT generated
Raw token sent securely to client
SHA-256 token hash stored in MongoDB
Client later sends refresh token
JWT signature verified
Received token hashed
Database session located
Check revoked status
Check expiration
Accept, rotate, or reject

We’ll use:

→ Test runner and assertions

Supertest
→ Sends HTTP requests directly to the Express app

mongodb-memory-server
→ Runs an isolated temporary MongoDB replica set

We need a replica set because the Category update, delete, restore, and hierarchy operations use MongoDB transactions. MongoMemoryReplSet supports this when configured with the WiredTiger storage engine.

1. Confirm your Node.js version

Run:
node -v
Use Node.js:
20.19.0 or newer
Current Vitest requires Node.js 20+, while the current mongodb-memory-server documentation specifies Node.js 20.19.0 or newer.

2. Install test dependencies

From the backend folder:
npm install --save-dev vitest supertest mongodb-memory-server
Supertest can test the Express application directly without manually starting the backend on a fixed port. When passed an Express app, it can bind an ephemeral port automatically.

3. Update package.json

Open:
package.json
Add these scripts:

{
  "scripts": {
    "dev": "nodemon src/server.js",
    "start": "node src/server.js",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:integration": "vitest run tests/integration"
  }
}

Keep all your existing scripts. Only add the test scripts.

4. Confirm the test environment is accepted

When "test" is already included, no change is needed.

5. Create Vitest configuration
Create:
vitest.config.js
Vitest supports a dedicated configuration file when the project is not using Vite. It also provides separate globalSetup and setupFiles hooks; global setup executes before workers, while setup files execute in the test process before each test file.

6. Create the global MongoDB setup
Create the folder:
tests/setup
Create:
tests/setup/global.setup.js
The database is temporary and separate from your MongoDB Atlas database. The in-memory server starts an actual MongoDB process for isolated testing and stops it after the test suite.

Vitest global setup executes in a separate scope, so project.provide() and inject() are the supported way to pass serializable information such as the temporary MongoDB URI into test workers.

7. Create the per-test-file setup
Create:
tests/setup/test.setup.js

Integration tests should not depend on your local .env values.

For watch mode:

First-run note

On the first execution, mongodb-memory-server may download a MongoDB binary and cache it locally. Later test runs should reuse the cached binary.

Do not cancel the first test run merely because the MongoDB binary initialization takes longer than later runs.

Part 77: Atomic Inventory Ledger Integration

src/modules/products/product-inventory-ledger.repository.js

src/modules/products/product.service.js

After this step, each inventory operation becomes one transaction:

Update Product inventory
        +
Create Inventory Ledger entry
        ↓
Both succeed or both roll back

Transaction behavior
Successful operation
1. MongoDB transaction starts
2. Product inventory is updated atomically
3. Ledger entry is validated
4. Ledger entry is inserted
5. Transaction commits

Both records become visible together.

Ledger creation failure

Suppose the Product update succeeds internally but the ledger entry fails validation:

1. Product inventory is updated inside transaction
2. Ledger validation fails
3. Transaction aborts
4. Product inventory update is rolled back

The database will not contain an untracked inventory change.

Inventory update failure

Suppose available stock is insufficient:

1. Transaction starts
2. Atomic Product update returns null
3. Service diagnoses the failure
4. PRODUCT_INSUFFICIENT_AVAILABLE_STOCK is thrown
5. Transaction aborts
6. No ledger entry is created

Part 164 — Replacement State-Machine Race Hardening

I checked the current orders.zip. The important issue is the order inside your three inventory-changing workflows.

Right now they effectively do:

Read replacement
→ change Product inventory
→ create Ledger
→ save final replacement status

For stronger cross-operation concurrency safety, change them to:

Atomically claim final replacement state
→ change Product inventory
→ create Ledger
→ commit transaction

If inventory fails, MongoDB rolls the state claim back too.

This protects:

ship   vs cancel
ship   vs fail
cancel vs fail

Only update:

src/modules/orders/order-return-replacement.repository.js
src/modules/orders/order-return-replacement.service.js

No controller, validation, mapper, model, or route changes.

Why this is safer

Consider ship vs cancel at exactly the same time.

Previously both could initially read:

status = processing

and both would begin touching Product inventory.

Now:

Ship transaction
    ↓
atomic:
processing → shipped

Cancel transaction
    ↓
atomic:
processing → cancelled

Only one can successfully claim that same Replacement document.

If ship wins:

Replacement = shipped

stock         10 → 8
reservedStock  2 → 0

Ledger:
reserve
commit

Cancellation retries against the latest state and gets:

409
ORDER_RETURN_REPLACEMENT_CANCELLATION_STATUS_INVALID

No release.

If cancel wins:

Replacement = cancelled

stock         10 → 10
reservedStock  2 → 0

Ledger:
reserve
release

Shipment gets:

409
ORDER_RETURN_REPLACEMENT_SHIPMENT_STATUS_INVALID

No commit.

The same protection now applies to:

ship   vs fail
cancel vs fail
Rollback still works

State claim occurs first, but it is inside the same MongoDB transaction.

Example:

processing
   ↓
transaction sets shipped
   ↓
inventory commit fails

MongoDB rolls everything back:

Replacement status → processing
shipment            → removed
stock               → original value
reservedStock       → original value
commit Ledger        → removed

So the state claim is not prematurely permanent.
